# 长春理工大学 Minecraft 社团官网开发规范文档

## 1. 总体原则

- 开发实现应遵循产品需求文档、总体设计文档和详细设计文档。
- 页面路由、接口路径、数据模型字段应优先遵循详细设计文档。
- 本文档只约束代码风格、工程组织、提交方式和文档同步方式。
- 系统功能、权限、接口、缓存、安全和媒体规则以详细设计文档为准。

## 2. 代码注释风格

### 2.1 注释原则

- 注释用于解释“为什么这样做”，不重复描述代码“做了什么”。
- 不为显而易见的代码写注释。
- 需要说明业务原因、边界条件、兼容逻辑、迁移原因、性能原因或安全原因时，应添加注释。
- 临时方案必须说明原因和后续处理方式。
- 注释语言统一使用中文，代码标识符使用英文。

推荐：

```ts
// Strapi 返回结构不稳定，前台统一在这里裁剪字段，避免页面直接依赖 CMS 内部格式。
function normalizeActivity(raw: StrapiActivity): ActivitySummary {
  // ...
}
```

不推荐：

```ts
// 获取活动
const activities = await fetchActivities()

// 设置标题
title.value = data.title
```

### 2.2 TODO 规范

- 不允许只写 `TODO`。
- TODO 必须说明触发条件、后续处理方式或迁移目标。
- 无法确定处理时间时，应说明依赖条件。

推荐：

```ts
// TODO: 自研后台上线后，将这里的数据源从 Strapi 切换为 NestJS API。
```

不推荐：

```ts
// TODO
```

## 3. 命名规范

- 变量、函数使用 `camelCase`。
- Vue 组件、类型、接口使用 `PascalCase`。
- 常量使用 `UPPER_SNAKE_CASE`，仅用于真正的全局常量。
- 文件名使用 `kebab-case`，例如 `activity-card.vue`。
- 页面路由文件遵循 Nuxt 约定。
- 不使用拼音命名，除非是无法准确翻译的专有名词。
- 命名应表达业务含义，避免使用 `data`、`item`、`list` 等过于泛化的名称作为长期变量名。

示例：

```ts
const activityList = ref<ActivitySummary[]>([])

function getActivityStatusLabel(status: ActivityStatus) {
  // ...
}
```

## 4. TypeScript 规范

- 所有接口返回值必须有类型定义。
- 不随意使用 `any`，确实无法确定类型时优先使用 `unknown`。
- CMS 原始类型和前台展示类型应分开定义。
- 枚举值优先使用字符串联合类型。
- 对可空字段显式标记 `null` 或 `undefined`。
- 公共类型应放在统一的 `types` 目录或模块中。

示例：

```ts
type ActivityStatus = 'upcoming' | 'ongoing' | 'ended' | 'cancelled'

interface ActivitySummary {
  title: string
  slug: string
  summary?: string
  coverImage: MediaImage
  status: ActivityStatus
}
```

## 5. Vue 与 Nuxt 规范

- 页面负责数据获取、SEO 配置和页面级状态。
- 展示组件只接收 props，不直接请求接口。
- 复杂逻辑应抽到 composable。
- 组件 props 和 emits 必须有类型。
- 不在模板中编写复杂表达式。
- 页面中的 SEO 配置应与页面数据绑定。
- 列表页必须处理加载中、空状态、错误状态和分页状态。
- 详情页必须处理 404。

推荐结构：

```text
pages/activities/index.vue
components/activity/activity-card.vue
composables/use-activities.ts
types/activity.ts
```

## 6. CSS 与 UI 规范

- Tailwind CSS 用于布局、间距、响应式和常规样式。
- 复杂像素风效果使用自定义 CSS class。
- 页面级颜色、边框、阴影、像素风变量应抽成设计变量。
- 不在组件中重复写大量一次性颜色值。
- 具体视觉、响应式、图标和媒体要求以详细设计文档为准。

## 7. 接口调用规范

- 所有接口调用应集中封装，不在组件中散落 `fetch`。
- API 方法命名应与接口资源对应。
- 页面代码只消费前台标准数据结构，数据转换逻辑集中放在 adapter 或 normalize 函数中。
- 接口错误应统一处理，不把后端错误对象直接暴露给页面。
- 接口路径、权限校验和缓存策略以详细设计文档为准。
- mock fallback 只能用于开发或测试环境；生产环境公开接口不得用 mock 数据冒充 Strapi 真实公开内容。
- 生产环境 Strapi 连接失败、超时或无响应时，应返回维护态语义；Strapi 正常响应但内容不存在时，才返回 404。

示例：

```ts
const { data, error, pending } = await useActivities({
  page: 1,
  pageSize: 10,
})
```

## 8. 错误处理规范

- 页面应按照详细设计文档处理加载中、空状态、错误状态、401、403 和 404。
- 不把接口错误直接原样展示给用户。
- 控制台日志不能代替用户可见反馈。
- 图片加载失败时应使用默认占位图。

## 9. Git 与提交规范

提交信息建议使用 Conventional Commits：

```text
feat: add activity list page
fix: handle missing post cover image
docs: update detailed design document
refactor: extract activity api adapter
style: format activity components
```

提交约束：

- 一个提交只做一类修改。
- 文档、格式化、大重构不要混在功能提交里。
- 不提交 `.env`、密钥、日志和构建产物。
- 修改数据模型、接口结构、路由时，应同步更新文档。
- 不在功能分支中混入无关格式化或大规模重构。

## 10. 文档同步规范

- 新增页面时必须更新详细设计文档。
- 新增接口时必须更新接口定义。
- 新增 CMS 字段时必须更新数据模型说明。
- 修改图片尺寸、格式、上传规则时必须更新媒体规范。
- 修改权限逻辑时必须更新权限说明。
- 修改技术栈或部署方式时必须更新总体设计文档。

## 11. 实现状态标注规范

- 文档描述当前实现时，应区分“已实现”“部分实现”“预留”“暂缓”“待生产接入”。
- mock 数据、占位交互、预留模型和待接入外部服务不得写成生产可用能力。
- 如果代码保留 mock fallback，必须有明确环境边界，避免生产构建启用。
- 修改需求范围时，应先更新产品需求文档；修改页面、接口、模型或权限细节时，应同步更新详细设计文档。
- 修改运行架构、目录职责、部署方式或运行配置时，应同步更新总体设计文档。
- 修改代码组织、类型约束、接口调用方式、注释或提交规范时，应同步更新本文档。
- 使用 OpenSpec 创建或执行变更时，tasks 中应包含阅读相关 docs 和同步更新相关 docs 的检查项。
