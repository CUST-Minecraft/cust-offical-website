# 长春理工大学 Minecraft 社团官网自研后台设计文档

## 1. 建设定位

自研后台不作为第一阶段必须建设内容。第一阶段由 Strapi 承担内容管理、内容模型、媒体库和草稿发布能力。

后续当社团需要活动报名、白名单审核、复杂成员系统、精细化权限或更强的业务流程时，再将自研后台作为独立系统引入。

## 2. 技术栈选型

| 类型 | 选型 | 用途 |
| --- | --- | --- |
| 自研后台 UI | Vue 3 + Element Plus | 内容管理、成员管理、活动管理等后台页面 |
| 自研业务后端 | NestJS | 业务流程、权限控制、审核流、对外 API |
| 数据库 | PostgreSQL | 复用主数据库或按业务拆分独立库 |
| 缓存与队列 | Redis | 后续用于缓存、队列、限流、Session 等 |

## 3. 核心职责

- 内容管理：替代 Strapi 的内容后台能力，管理社团介绍、公告、活动、社团动态、社员介绍等内容。
- 成员管理：维护社员资料、角色、权限和后台访问范围。
- 活动管理：支持活动创建、报名、审核、名单导出等流程。
- 白名单审核：支持 Minecraft 服务器相关准入、审核和状态同步。
- 权限控制：区分管理员、内容管理员、普通社员等后台权限。

## 4. 与官网前台的边界

官网前台应继续只依赖 `/api/public/*` 和 `/api/member/*` 等稳定接口，不直接绑定自研后台内部数据结构。

自研后台上线后，可以逐步替换 Strapi 的内容 API，但不应要求前台大规模改造页面逻辑。

## 5. 迁移原则

- 第一阶段优先保证官网前台上线，不提前开发完整自研后台。
- 前台接口先由 Nuxt Server Routes 聚合 Strapi 数据，后续再切换为聚合自研后台数据。
- 自研后台优先承接 Strapi 无法很好覆盖的业务流程，再逐步替换 CMS 能力。
- 数据迁移应以内容模型稳定为前提，避免频繁改动公开页面字段。
