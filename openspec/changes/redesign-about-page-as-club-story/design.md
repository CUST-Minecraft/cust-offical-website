## Context

`/about` 当前实现包含通用 `PageHero`、一段故事展示、分组卡片、服务器概览和加入引导。`docs/产品需求文档.md` 与 `docs/详细设计文档.md` 目前仍要求社团介绍页展示社团背景、方向、文化、分组、服务器概览和加入引导；但经过本次探索，页面定位更适合收敛为品牌故事入口，而不是服务器说明或加入流程页。

当前 `AboutPage` 模型包含 `title`、`summary`、`coverImage`、`content`、`groups`、`serverSummary` 和 `joinGuide`。这些字段能支撑旧页面，但和新的五段式板块结构不再一一对应。社团介绍页后续应改为以 `sections[]` 作为主数据源：一条 section 数据对应一个页面板块，前台按固定 `sectionType` 渲染固定模板，后台维护每个板块的标题、正文、卡片和链接。页面仍需遵守第一阶段边界：不建设自研后台，不暴露敏感成员信息，不把皮肤站、资源包下载或白名单审核能力混入本变更。

## Goals / Non-Goals

**Goals:**

- 将 `/about` 重排为五段式故事结构：`认识我们`、`我们的起点`、`我们的行动`、`我们的方向`、`继续了解`。
- 让页面先呈现社团身份和创立语境，再展示社团主要行动和参与方向。
- 将“校园复刻 / 服务器共建 / 活动与创作”作为“我们的行动”内容，避免让服务器参数成为页面后半段主角。
- 将页面末尾设计为“继续了解”出口，导向 `/join`、`/activities` 和 `/members` 等公开页面。
- 将 `AboutPage` 调整为按板块维护：`sections[]` 中每一项对应一个页面板块。
- 让“我们的行动”“我们的方向”“继续了解”等结构化内容从 section items/links 读取，而不是前端写死或从富文本拼装。
- 同步更新 docs 中关于社团介绍页的目标、功能说明、数据来源和边界描述。
- 保持现有公开路由、BFF 接口路径和 SEO 基本规则稳定；BFF 输出结构可以随板块模型扩展，但路径仍为 `GET /api/public/about`。

**Non-Goals:**

- 不实现报名、白名单审核、成员登录或自研后台能力。
- 不在 `/about` 中展示真实姓名、学号、手机号等敏感信息。
- 不把皮肤站、文档中心、下载服务或服务器在线查询纳入社团介绍页范围。
- 不要求本次必须引入复杂动画、3D 场景或新的外部依赖。
- 不把 `/about` 变成 `/join` 的替代页面；加入流程仍由 `/join` 承担。

## Decisions

### 决策 1：使用五段式栏目结构

页面主结构固定为：

```text
认识我们
我们的起点
我们的行动
我们的方向
继续了解
```

`认识我们` 对应 Hero 和社团身份；`我们的起点` 承载社团简介正文；`我们的行动` 展示校园复刻、服务器共建、活动与创作；`我们的方向` 展示建筑、红石、活动、运维等参与方向；`继续了解` 提供公开页面出口。

替代方案是保留现有“故事 + 分组 + 服务器概览 + 加入引导”结构。该方案实现成本低，但无法解决 `/about` 被服务器参数和加入引导牵走的问题，也不符合这次确定的品牌故事定位。

### 决策 2：服务器信息降级为行动语境，不再作为独立概览

服务器仍可作为“我们的行动”中的一类共创内容出现，但 `/about` 不再展示固定 IP、版本、模式等参数列表。服务器地址、版本、模式、维护状态和加入说明更适合由 `/join`、维护页、社团服务工作台或后续独立服务器说明能力承载。

替代方案是把服务器概览改成更漂亮的视觉段落。该方案保留了旧重心，仍会让介绍页承担工具信息职责，因此不采用。

### 决策 3：优先复用现有内容模型，谨慎扩展 CMS 字段

社团介绍页采用按板块建模，而不是继续把数据拆成 `content`、`groups`、`serverSummary`、`joinGuide` 这类页面专用散字段。推荐模型：

```text
AboutPage
├─ title / summary / coverImage / SEO 字段
└─ sections[]
   ├─ sectionType: hero | origin | actions | directions | next
   ├─ eyebrow
   ├─ title
   ├─ summary
   ├─ content
   ├─ image
   ├─ items[]
   ├─ links[]
   ├─ sortOrder
   └─ enabled
```

`items[]` 用于“我们的行动”和“我们的方向”等卡片内容，字段包括 `title`、`summary`、`code`、`icon`、`image`、`sortOrder` 和 `enabled`。`links[]` 用于“继续了解”，字段包括 `label`、`summary`、`href`、`code`、`openInNewTab`、`sortOrder` 和 `enabled`。

替代方案是保留前端稳定配置，让“我们的行动”和“继续了解”继续写在 Vue 文件里。该方案实现快，但和用户希望“一项是一个板块”的维护方式不一致，也会让内容管理员无法从后台按板块理解和维护页面，因此不作为最终方案。

### 决策 4：前台固定模板，后台只维护内容

`sections[]` 不是自由页面搭建器。前台只识别固定 `sectionType`，并使用固定模板渲染五个板块。后台可维护板块标题、摘要、正文、卡片、链接、排序和启用状态，但不维护 CSS、布局模板、动效或任意页面结构。

这样可以让后台数据与前台板块一一对应，同时避免内容管理员通过 Markdown 或自由组件破坏页面结构。

### 决策 5：文档同步是实现任务的一部分

本变更改变用户可见页面结构和页面职责，必须同步更新 `docs/产品需求文档.md` 与 `docs/详细设计文档.md`。产品文档应表达新页面目标和展示内容；详细设计应表达页面结构、数据来源、服务器信息降级规则、SEO、错误处理和可维护字段边界。

## Risks / Trade-offs

- [Risk] 从 `/about` 移除服务器参数后，访客可能少一个查看服务器信息的入口。→ 在“我们的行动”中保留服务器共建语境，并通过“继续了解”或现有站内页面导向更合适的信息入口。
- [Risk] `sections[]` 会增加 Strapi 模型、BFF 适配和 mock 数据复杂度。→ 将 section、item、link 拆成小组件，前台只支持固定 `sectionType`，避免泛化成页面搭建器。
- [Risk] 迁移后旧字段 `content`、`groups`、`serverSummary`、`joinGuide` 可能仍存在历史数据。→ 实现时提供 mock/兼容数据或迁移策略，确保 `GET /api/public/about` 不因为旧内容缺失而崩溃。
- [Risk] 后台可排序/启用 section 后，页面顺序可能被错误配置。→ 前台按允许的固定 `sectionType` 渲染，并可对缺失或重复 section 提供兜底顺序与过滤。
- [Risk] 页面栏目标题较整齐，但可能显得偏概念化。→ 每段正文和卡片文案使用具体行为描述，如校园复刻、服务器共建、活动与创作，避免空泛口号。
- [Risk] 视觉重设计可能与现有全站像素风组件重复或冲突。→ 复用现有 `PageHero`、像素边框、motion reveal、按钮和卡片风格，只在必要处新增页面局部样式。
- [Risk] docs 仍保留旧服务器概览和加入引导描述会造成实现验收冲突。→ 将 docs 更新列为明确任务，先改文档再验收页面。
